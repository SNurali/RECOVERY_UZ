# Requirements Document

## Introduction

Полный редизайн пользовательского интерфейса CRM-системы сервисного центра по восстановлению данных RECOVERY.UZ. Цель — создать красивый, простой и интуитивно понятный интерфейс для клиентов, а также удобную и функциональную панель управления для сотрудников (операторов, мастеров, администраторов). Система поддерживает 4 роли: клиент, оператор, мастер, администратор. Заказы проходят жизненный цикл: новый → диагностика → ожидание одобрения → одобрен → в ремонте → завершён → выдан.

## Glossary

- **Система**: Веб-приложение RECOVERY.UZ (фронтенд на React + бэкенд на Express/PostgreSQL)
- **Клиент**: Пользователь с ролью `client`, сдающий оборудование в ремонт
- **Оператор**: Пользователь с ролью `operator`, принимающий и распределяющий заказы
- **Мастер**: Пользователь с ролью `master`, выполняющий ремонтные работы
- **Администратор**: Пользователь с ролью `admin`, имеющий полный доступ ко всем разделам системы
- **Заказ**: Запись в системе, содержащая информацию о сданном оборудовании, неисправности, назначенном мастере, статусе и стоимости
- **Деталь_заказа**: Отдельная позиция в заказе (оборудование + неисправность + услуга + мастер + цена)
- **Справочник**: Каталог типов оборудования, неисправностей и услуг с мультиязычными названиями
- **Панель_сотрудника**: Интерфейс для ролей admin, operator, master с боковой навигацией
- **Клиентский_интерфейс**: Интерфейс для роли client с упрощённой навигацией
- **Гостевая_страница**: Публичная страница для неавторизованных пользователей

## Requirements

### Requirement 1: Гостевая страница и лендинг

**User Story:** Как потенциальный клиент, я хочу видеть красивую и понятную главную страницу, чтобы быстро понять назначение сервиса и начать взаимодействие.

#### Acceptance Criteria

1. WHEN неавторизованный пользователь открывает главную страницу, THE Система SHALL отобразить Гостевую_страницу с логотипом, описанием сервиса, кнопкой создания заявки и полем отслеживания заказа
2. THE Гостевая_страница SHALL содержать визуальные блоки преимуществ сервиса (безопасность, скорость, поддержка 24/7)
3. WHEN пользователь нажимает кнопку «Создать заявку», THE Система SHALL перенаправить пользователя на страницу авторизации с параметром действия создания заказа
4. WHEN пользователь вводит ID заказа в поле отслеживания и нажимает кнопку поиска, THE Система SHALL перенаправить пользователя на страницу отслеживания заказа с указанным токеном
5. THE Гостевая_страница SHALL содержать ссылку для входа сотрудников в нижней части страницы
6. THE Гостевая_страница SHALL использовать анимации при появлении элементов для создания современного визуального впечатления

### Requirement 2: Авторизация и регистрация

**User Story:** Как пользователь, я хочу иметь простую и понятную форму входа и регистрации, чтобы быстро получить доступ к системе.

#### Acceptance Criteria

1. THE Система SHALL предоставить страницу входа с полями логин (телефон или email) и пароль
2. WHEN пользователь вводит корректные учётные данные и нажимает «Войти», THE Система SHALL аутентифицировать пользователя и перенаправить на соответствующую панель в зависимости от роли (client → Клиентский_интерфейс, admin/operator/master → Панель_сотрудника)
3. IF пользователь вводит некорректные учётные данные, THEN THE Система SHALL отобразить сообщение об ошибке «Неверный логин или пароль»
4. THE Система SHALL предоставить страницу регистрации с полями: полное имя, телефон, пароль, подтверждение пароля
5. IF пароль содержит менее 6 символов, THEN THE Система SHALL отобразить сообщение валидации «Пароль должен быть не менее 6 символов»
6. IF пароли в полях «Пароль» и «Подтверждение пароля» не совпадают, THEN THE Система SHALL отобразить сообщение «Пароли не совпадают»
7. WHEN сессия пользователя истекает, THE Система SHALL перенаправить пользователя на страницу входа с уведомлением «Сеанс истёк. Войдите заново»

### Requirement 3: Клиентский интерфейс — Список заказов

**User Story:** Как клиент, я хочу видеть все свои заказы в простом и красивом виде, чтобы легко отслеживать их статус.

#### Acceptance Criteria

1. WHEN авторизованный Клиент открывает Клиентский_интерфейс, THE Система SHALL отобразить список всех заказов данного клиента в виде карточек
2. THE Система SHALL отображать для каждого заказа: сокращённый ID, тип оборудования, текущий статус в виде цветного бейджа и индикатор ожидания одобрения цены
3. WHEN Клиент нажимает на карточку заказа, THE Система SHALL перенаправить Клиента на страницу детальной информации о заказе
4. IF у Клиента нет заказов, THEN THE Система SHALL отобразить пустое состояние с предложением создать первый заказ
5. THE Клиентский_интерфейс SHALL содержать кнопку «Новый заказ» в верхней части страницы
6. THE Клиентский_интерфейс SHALL использовать тёмную тему с градиентным фоном и стеклянным эффектом (glassmorphism) для карточек

### Requirement 4: Клиентский интерфейс — Создание заказа

**User Story:** Как клиент, я хочу быстро и просто оформить заявку на ремонт оборудования, чтобы не тратить время на сложные формы.

#### Acceptance Criteria

1. WHEN Клиент открывает страницу создания заказа, THE Система SHALL отобразить форму с полями: тип оборудования (выпадающий список), тип неисправности (выпадающий список), серийный номер (необязательное поле), дополнительные примечания (текстовое поле)
2. THE Система SHALL загрузить списки типов оборудования и неисправностей из Справочника при открытии формы
3. WHEN Клиент заполняет обязательные поля (тип оборудования, тип неисправности) и нажимает «Отправить заявку», THE Система SHALL создать новый Заказ со статусом «new» и перенаправить Клиента на главную страницу с уведомлением об успешной отправке
4. IF загрузка справочников завершается ошибкой, THEN THE Система SHALL отобразить уведомление об ошибке загрузки данных
5. THE форма создания заказа SHALL быть ограничена максимальной шириной 600px и центрирована на странице

### Requirement 5: Клиентский интерфейс — Детали заказа и согласование цены

**User Story:** Как клиент, я хочу видеть подробную информацию о своём заказе и иметь возможность одобрить или отклонить предложенную стоимость ремонта.

#### Acceptance Criteria

1. WHEN Клиент открывает страницу деталей заказа, THE Система SHALL отобразить: сокращённый ID заказа, дату создания, текущий статус, временную шкалу прогресса (timeline) и информацию об оборудовании
2. THE временная шкала прогресса SHALL отображать 5 этапов: Приём оборудования → Диагностика → Согласование цены → Ремонт → Готов к выдаче, с визуальным выделением пройденных и текущего этапов
3. WHILE заказ находится в состоянии ожидания одобрения цены (цена установлена, но не одобрена и не отклонена), THE Система SHALL отобразить блок согласования с суммой, кнопкой «Подтвердить цену» и кнопкой «Отказаться»
4. WHEN Клиент нажимает «Подтвердить цену», THE Система SHALL отправить запрос одобрения цены и отобразить уведомление «Цена успешно одобрена. Мастер приступает к ремонту.»
5. WHEN Клиент нажимает «Отказаться», THE Система SHALL запросить причину отказа через диалоговое окно и отправить запрос отклонения цены
6. WHILE цена одобрена, THE Система SHALL отобразить зелёный блок подтверждения с текстом «Цена согласована» и суммой

### Requirement 6: Панель сотрудника — Навигация и макет

**User Story:** Как сотрудник (оператор, мастер, администратор), я хочу иметь удобную панель с боковой навигацией, чтобы быстро переключаться между разделами.

#### Acceptance Criteria

1. THE Панель_сотрудника SHALL содержать боковую панель навигации (sidebar) с логотипом, ролью пользователя и навигационными ссылками
2. THE боковая панель SHALL содержать ссылки: Главная (Dashboard), Заказы — для всех ролей сотрудников
3. WHERE роль пользователя — admin или operator, THE Панель_сотрудника SHALL дополнительно отображать ссылку «Клиенты»
4. WHERE роль пользователя — admin, THE Панель_сотрудника SHALL дополнительно отображать ссылки «Услуги» (Справочники) и «Настройки» (Пользователи)
5. THE Панель_сотрудника SHALL содержать верхнюю панель (topbar) с приветствием, переключателем языка, именем пользователя и кнопкой выхода
6. THE активная ссылка навигации SHALL быть визуально выделена для индикации текущего раздела

### Requirement 7: Панель сотрудника — Дашборд

**User Story:** Как сотрудник, я хочу видеть сводную статистику по заказам на главной странице, чтобы быстро оценить текущую загрузку.

#### Acceptance Criteria

1. WHEN сотрудник открывает Панель_сотрудника, THE Система SHALL отобразить дашборд со статистическими карточками
2. THE дашборд SHALL отображать карточки: общее количество заказов, количество активных заказов (в ремонте), количество завершённых заказов за сегодня
3. THE каждая статистическая карточка SHALL содержать иконку, подпись и числовое значение
4. IF загрузка статистики завершается ошибкой, THEN THE Система SHALL отобразить уведомление об ошибке сети

### Requirement 8: Панель сотрудника — Список заказов (табличный вид)

**User Story:** Как оператор или администратор, я хочу видеть все заказы в табличном виде с возможностью быстрого поиска и фильтрации, чтобы эффективно управлять потоком заказов.

#### Acceptance Criteria

1. WHEN сотрудник открывает раздел «Заказы», THE Система SHALL отобразить таблицу всех заказов с колонками: ID, Дата, Клиент (ФИО и телефон), Оборудование, Неисправность, Мастер, Статус, Цена
2. THE статус заказа SHALL отображаться в виде цветного бейджа с текстовым обозначением на русском языке (Новый, Диагностика, Ждёт одобрения, Одобрен, В ремонте, Завершён, Выдан)
3. WHEN сотрудник нажимает на строку таблицы, THE Система SHALL перенаправить сотрудника на страницу детальной информации о заказе
4. THE страница списка заказов SHALL содержать кнопку «Создать заказ» в верхней части
5. THE таблица заказов SHALL поддерживать сортировку по колонкам

### Requirement 9: Панель сотрудника — Детали заказа и управление

**User Story:** Как оператор или администратор, я хочу управлять заказом: менять статус, назначать мастера, устанавливать цену и закрывать заказ.

#### Acceptance Criteria

1. WHEN сотрудник открывает страницу деталей заказа, THE Система SHALL отобразить: ID заказа, дату создания, текущий статус, информацию о клиенте (ФИО, телефон, email, статус Telegram), таблицу услуг и оборудования
2. THE Система SHALL отобразить доступные переходы статуса в виде кнопок на основе текущего статуса заказа
3. WHEN сотрудник нажимает кнопку перехода статуса, THE Система SHALL запросить подтверждение и обновить статус заказа
4. WHERE роль пользователя — admin или operator, THE Система SHALL отобразить выпадающий список мастеров для назначения на каждую Деталь_заказа
5. WHEN сотрудник назначает мастера на Деталь_заказа, THE Система SHALL сохранить назначение и отобразить уведомление «Мастер успешно назначен»
6. THE Система SHALL отобразить поля ввода цены для каждой Детали_заказа с кнопкой «Сохранить цены»
7. WHEN сотрудник нажимает «Сохранить цены», THE Система SHALL сохранить цены для всех деталей заказа и обновить итоговую сумму
8. WHILE заказ имеет статус «completed» и оплата полностью внесена, THE Система SHALL отобразить кнопку «Выдать и закрыть»
9. WHEN сотрудник нажимает «Выдать и закрыть», THE Система SHALL запросить подтверждение, закрыть заказ и отобразить уведомление «Заказ успешно закрыт и выдан»
10. WHILE цена одобрена клиентом, THE Система SHALL отобразить зелёную отметку с датой одобрения
11. WHILE цена ожидает одобрения клиентом, THE Система SHALL отобразить предупреждение «Ожидает одобрения цены клиентом»

### Requirement 10: Управление клиентами

**User Story:** Как оператор или администратор, я хочу управлять базой клиентов — просматривать, добавлять и редактировать информацию о клиентах.

#### Acceptance Criteria

1. WHERE роль пользователя — admin или operator, WHEN сотрудник открывает раздел «Клиенты», THE Система SHALL отобразить таблицу клиентов с колонками: ФИО, Телефон, Email, Telegram
2. THE Система SHALL отображать статус подключения Telegram для каждого клиента (подключён/не подключён)
3. WHEN сотрудник нажимает «Добавить клиента», THE Система SHALL отобразить форму с полями: ФИО (обязательное), Телефон (обязательное), Email (необязательное), Telegram Chat ID (необязательное)
4. WHEN сотрудник заполняет обязательные поля и нажимает «Сохранить», THE Система SHALL создать нового клиента и обновить таблицу

### Requirement 11: Управление справочниками (каталог)

**User Story:** Как администратор, я хочу управлять справочниками (услуги, оборудование, неисправности), чтобы поддерживать актуальный каталог для создания заказов.

#### Acceptance Criteria

1. WHERE роль пользователя — admin, WHEN Администратор открывает раздел «Услуги», THE Система SHALL отобразить страницу справочников с вкладками: Услуги, Оборудование, Неисправности
2. THE каждая вкладка SHALL отображать таблицу записей с колонками: Русский, Узбекский (Кириллица), Узбекский (Латиница), Английский, Действия
3. WHEN Администратор нажимает «Добавить запись», THE Система SHALL отобразить строку ввода с полями для всех 4 языков и кнопками сохранения/отмены
4. WHEN Администратор нажимает «Изменить» на существующей записи, THE Система SHALL преобразовать строку в режим редактирования с заполненными полями
5. WHEN Администратор нажимает «Удалить» на записи, THE Система SHALL запросить подтверждение и удалить запись из справочника
6. WHEN Администратор сохраняет новую или отредактированную запись, THE Система SHALL обновить справочник и отобразить уведомление об успешном сохранении

### Requirement 12: Управление пользователями (сотрудниками)

**User Story:** Как администратор, я хочу управлять учётными записями сотрудников (операторов, мастеров, администраторов), чтобы контролировать доступ к системе.

#### Acceptance Criteria

1. WHERE роль пользователя — admin, WHEN Администратор открывает раздел «Настройки», THE Система SHALL отобразить таблицу сотрудников с колонками: ФИО, Роль, Телефон, Email
2. THE роль сотрудника SHALL отображаться в виде бейджа
3. WHEN Администратор нажимает «Создать сотрудника», THE Система SHALL отобразить форму с полями: ФИО, Логин, Пароль, Роль (Администратор/Оператор/Мастер), Телефон, Email
4. WHEN Администратор заполняет обязательные поля (ФИО, Логин, Пароль, Роль) и нажимает «Создать», THE Система SHALL создать нового сотрудника и обновить таблицу

### Requirement 13: Мультиязычность

**User Story:** Как пользователь, я хочу переключать язык интерфейса, чтобы использовать систему на удобном для меня языке.

#### Acceptance Criteria

1. THE Система SHALL поддерживать 4 языка: Русский (ru), Узбекский латиница (uz-lat), Узбекский кириллица (uz-cyr), Английский (en)
2. THE переключатель языка SHALL быть доступен на всех страницах системы (в верхней панели для сотрудников, в шапке для клиентов)
3. WHEN пользователь выбирает другой язык, THE Система SHALL мгновенно переключить все текстовые элементы интерфейса на выбранный язык без перезагрузки страницы
4. THE Система SHALL сохранять выбранный язык пользователя между сессиями

### Requirement 14: Адаптивный дизайн

**User Story:** Как пользователь, я хочу комфортно использовать систему на любом устройстве (компьютер, планшет, телефон).

#### Acceptance Criteria

1. THE Клиентский_интерфейс SHALL корректно отображаться на экранах шириной от 320px до 2560px
2. THE Панель_сотрудника SHALL корректно отображаться на экранах шириной от 768px до 2560px
3. THE таблицы данных SHALL использовать горизонтальную прокрутку на экранах, где ширина таблицы превышает ширину контейнера
4. THE сетка карточек SHALL автоматически адаптировать количество колонок в зависимости от ширины экрана (минимальная ширина карточки 240px для дашборда, 300px для деталей заказа)

### Requirement 15: Разграничение доступа по ролям

**User Story:** Как администратор, я хочу, чтобы каждая роль имела доступ только к разрешённым разделам, чтобы обеспечить безопасность данных.

#### Acceptance Criteria

1. THE Система SHALL ограничить доступ к Панели_сотрудника только для ролей admin, operator, master
2. THE Система SHALL ограничить доступ к Клиентскому_интерфейсу только для ролей client и admin
3. IF неавторизованный пользователь пытается открыть защищённый маршрут, THEN THE Система SHALL перенаправить пользователя на страницу входа
4. IF пользователь с ролью client пытается открыть маршрут Панели_сотрудника, THEN THE Система SHALL перенаправить пользователя на Клиентский_интерфейс
5. IF пользователь с ролью operator или master пытается открыть маршрут Клиентского_интерфейса, THEN THE Система SHALL перенаправить пользователя на Панель_сотрудника
6. WHERE роль пользователя — admin, THE Система SHALL предоставить полный доступ ко всем разделам системы, включая редактирование любых заказов, управление справочниками и пользователями

### Requirement 16: Уведомления и обратная связь

**User Story:** Как пользователь, я хочу получать мгновенную обратную связь о результатах моих действий, чтобы понимать, что операция выполнена успешно или произошла ошибка.

#### Acceptance Criteria

1. WHEN операция завершается успешно (создание заказа, обновление статуса, сохранение цены), THE Система SHALL отобразить всплывающее уведомление зелёного цвета с описанием результата
2. IF операция завершается ошибкой, THEN THE Система SHALL отобразить всплывающее уведомление красного цвета с описанием ошибки
3. IF сервер возвращает HTTP-статус 500 или выше, THEN THE Система SHALL отобразить уведомление «Сервер временно недоступен. Попробуйте позже»
4. THE уведомления SHALL автоматически исчезать через определённый промежуток времени без необходимости ручного закрытия

### Requirement 17: Отслеживание заказа без авторизации

**User Story:** Как клиент без учётной записи, я хочу проверить статус своего заказа по ID или токену, чтобы узнать текущее состояние ремонта.

#### Acceptance Criteria

1. THE Система SHALL предоставить публичную страницу отслеживания заказа, доступную без авторизации
2. WHEN пользователь вводит корректный ID или токен заказа, THE Система SHALL отобразить текущий статус заказа
3. IF введённый ID или токен не найден, THEN THE Система SHALL отобразить сообщение о том, что заказ не найден

### Requirement 18: Визуальный стиль и дизайн-система

**User Story:** Как пользователь, я хочу видеть единообразный, современный и приятный визуальный стиль во всех частях системы.

#### Acceptance Criteria

1. THE Клиентский_интерфейс SHALL использовать тёмную тему с градиентным фоном, стеклянными карточками (glassmorphism) и акцентным цветом бренда
2. THE Панель_сотрудника SHALL использовать чистый профессиональный стиль с боковой навигацией, светлыми карточками и чёткой типографикой
3. THE Система SHALL использовать единую систему цветовых бейджей для статусов заказов во всех интерфейсах
4. THE Система SHALL использовать иконки из библиотеки Lucide React для единообразия визуального языка
5. THE кнопки и интерактивные элементы SHALL иметь визуальные состояния: обычное, наведение (hover), нажатие (active), отключённое (disabled)
6. THE Система SHALL использовать плавные анимации переходов между состояниями элементов интерфейса
